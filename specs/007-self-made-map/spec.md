# Feature Specification: 자체 제작 맵 (방 인테리어·경기장 블록·섬·배경·조명)

**Feature Branch**: `claude/007-self-made-map`

**Created**: 2026-11-27

**Status**: Draft

**Input**: User description: "맵(방 인테리어와 004 경기장 블록·배경)을 자체 제작으로 새로 만든다. 캐릭터(005)를 완성도 있게 먼저,
맵은 그다음(병렬 가능). 디자인 퀄리티와 성능이 굉장히 중요하다. 시간이 걸려도 과감하게 자체 제작으로 간다. 무료 에셋 팩은 쓰지 않는다."

## 범위

- 3D 장면의 **맵 쪽 보이는 모습**을 이 프로젝트가 직접 만든 에셋으로 바꾼다: 방 테마 3개(카페·도서관·정원)의 인테리어(바닥·벽·창·
  고정 장식·가구), 004 경기장의 블록(흙·돌, 그리고 006 이후 늘어날 종류), 경기장 아래의 섬과 하늘·배경, 조명.
- 성능 예산(아래 "성능 예산")을 숫자로 정하고, 측정 도구로 PR마다 지킨다. 예산은 에셋 제작보다 먼저 정해져 있고 제작의 기준이 된다.
- 판정·규칙은 바꾸지 않는다: 테마의 경계·스폰·경기장 입구·충돌체, 경기장 격자(칸 1m)와 블록 판정, 방 데이터 형식은 그대로다.
- 범위 밖: 캐릭터(005), 새 테마·새 가구 종류·새 블록 종류(006이 블록 종류를 정하면 이 스펙의 기준으로 모습만 더한다), 2D 화면의 디자인 변경,
  이펙트(타격·꼬리)의 모습.
- 선행 조건: 에셋 제작은 005가 맡은 헌법 개정(자체 제작 에셋 허용) PR이 머지된 뒤 시작하고, 스타일은 005가 확정한 스타일 가이드를 따른다.
  그 전에는 스펙·성능 예산·측정 도구만 진행한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 경기장이 하늘에 뜬 섬처럼 보이고 블록을 한눈에 구분한다 (Priority: P1)

참가자가 경기장 입구를 밟아 경기장에 가면, 단색 상자가 깔린 판이 아니라 하늘에 뜬 섬 위의 경기장을 본다. 흙과 돌 블록은 색만이
아니라 모양·질감으로도 구분되고, 돌 블록은 칠 때마다 금이 가서 몇 번 더 치면 부서질지 보인다. 20명이 블록을 짓고 부숴도 화면이 끊기지 않는다.

**Why this priority**: 경기장은 004의 놀이가 일어나는 곳이고, 006이 블록 종류를 늘리기 전에 블록의 모습·성능 기준이 정해져야 한다.

**Independent Test**: 측정 도구로 경기장 시점의 드로우콜·삼각형과 20명 블록 변경 시 비용을 재고, 기준 화면을 운영자가 판정한다.

**Acceptance Scenarios**:

1. **Given** 경기장에 들어간 참가자, **When** 첫 화면을 보면, **Then** 경기장 판 아래와 둘레에 섬(땅·바위·풀)이 보이고 경계 밖은 빈 단색이 아니라 하늘·배경이다.
2. **Given** 흙과 돌 블록이 섞인 경기장, **When** 화면을 보면, **Then** 색을 구분하지 못하는 사람도 모양·질감으로 둘을 구분한다.
3. **Given** 내구 4인 돌 블록, **When** 한 번씩 칠 때마다, **Then** 블록 모습이 금 간 단계로 바뀌고 마지막에 부서진다.
4. **Given** 한 채널 20명이 각자 초당 4번 블록을 놓고 부술 때, **When** 경기장을 보면, **Then** 블록 변경 비용이 성능 예산 안이다.
5. **Given** 블록이 놓인 경기장, **When** 화면을 보면, **Then** 블록과 참가자는 섬·판 위에 그림자를 드리운다.

---

### User Story 2 - 방마다 테마가 정한 장소로 완성돼 보인다 (Priority: P2)

방문자가 카페·도서관·정원 방에 들어가면, 벽과 바닥만 있는 상자가 아니라 그 장소로 알아볼 수 있는 인테리어(창, 벽 장식, 바닥재,
조명 기구, 테마에 맞는 소품)를 본다. 가구는 같은 스타일로 만들어져 캐릭터(005)와 한 화풍으로 보인다.

**Why this priority**: 방은 첫인상이지만, 지금 방은 003으로 이미 최소 기준을 넘었고 경기장은 그렇지 않다.

**Independent Test**: 테마별 기준 화면(스폰 시점)을 운영자가 판정하고, 측정 도구로 방 시점의 예산을 잰다.

**Acceptance Scenarios**:

1. **Given** 각 테마 방, **When** 스폰 시점 화면을 보면, **Then** 테마 이름을 보지 않고도 카페·도서관·정원을 알아본다.
2. **Given** 이 기능 전에 만든 방(방 데이터에 옛 가구 id가 있는 방), **When** 들어가면, **Then** 같은 자리에 새 모습의 같은 가구가 보이고 충돌은 전과 같다.
3. **Given** 실내 테마, **When** 카메라가 벽 쪽으로 돌면, **Then** 지금처럼 벽 너머에서도 방 안이 보인다(003 research R3).

---

### User Story 3 - 저사양 휴대폰과 4G에서도 빨리 뜨고 부드럽다 (Priority: P1)

방문자가 보급형 휴대폰과 일반 4G로 들어와도 지금처럼 10초 안에 움직이고, 방과 경기장에서 끊김 없이 움직인다. 에셋이 늘어도 이 기준은
PR마다 자동으로 지켜진다.

**Why this priority**: 운영자가 디자인 품질과 함께 성능을 가장 중요하다고 꼽았다. 예산이 먼저 서야 에셋을 그 안에서 만든다.

**Independent Test**: 성능 예산의 측정 방법을 그대로 돌린다.

**Acceptance Scenarios**:

1. **Given** Fast 4G 휴대폰, **When** 목록에서 방에 들어가면, **Then** 10초 안에 첫 이동을 보내고 첫 3D 에셋 중 맵 몫이 예산 안이다.
2. **Given** 기준 저사양 휴대폰, **When** 20명 경기장에서 1분 싸우면, **Then** 프레임 예산을 지킨다.
3. **Given** 예산을 넘는 에셋을 넣은 PR, **When** 검사를 돌리면, **Then** 검사가 실패하고 어느 시점·항목이 넘었는지 알려 준다.

### Edge Cases

- WebGL이 없는 기기: 2D 화면은 바뀌지 않는다(004 FR-033). 2D 옆 그림의 블록 색·구분은 모습 목록에서 읽어 3D와 맞춘다.
- 블록이 많이 지어진 경기장(2,000개): 삼각형·드로우콜 예산의 "블록 2,000개" 줄을 지킨다.
- 실외 테마(정원)의 먼 배경: 안개 너머는 그리지 않는다.
- 006이 블록 종류를 늘리면: 종류마다 모습 목록 한 줄과 아틀라스 칸 하나를 더할 뿐, 블록 드로우콜 예산(종류 수 기준)은 그대로다.
- 에셋을 받지 못함(네트워크 오류): 지금처럼 로딩 화면과 오류 상태를 보이고, 판정·이동은 에셋 없이도 동작한다.

## Requirements *(mandatory)*

### Functional Requirements

**에셋과 출처**

- **FR-001**: 맵 에셋(인테리어·가구·블록·섬·배경)은 이 프로젝트가 직접 만든다. 무료 에셋 팩은 쓰지 않는다. 만든 에셋은 CC0로 공개하고,
  만든 방법(도구, 원본 파일 위치, 생성 프롬프트나 편집 절차, 가공 명령)을 `public/assets/CREDITS.md`에 파일마다 적는다(004 FR-038).
- **FR-002**: 에셋 제작은 005의 헌법 개정 PR이 머지된 뒤 시작하고, 형태·색·재질·디테일 밀도는 005의 스타일 가이드를 따른다. 3D 스타일은 아늑한 로우폴리다(003 FR-014).
- **FR-003**: 원본을 다시 가공하는 절차는 저장소의 스크립트로 재현된다(헌법 I). 지금의 `scripts/fetch-assets.sh`처럼 같은 명령이 같은 파일을 만든다.

**방 인테리어**

- **FR-004**: 테마마다 바닥재·벽(실내)·창·벽 장식·조명 기구·소품으로 된 고정 인테리어를 둔다. 고정 인테리어는 테마의 보이는 모습이고 방 데이터가 아니다.
  충돌체를 더하지 않으며, 참가자가 갈 수 있는 영역(테마 경계)과 스폰·경기장 입구를 가리지 않는다.
- **FR-005**: 지금 가구 id(`counter`, `table-round`, `chair`, `plant`, `bookshelf`, `desk`, `sofa`, `lamp`, `bench`, `flowers`, `tree`, `well`)는
  모두 새 모델로 바뀌고 같은 id로 계속 찾아진다. 옛 방의 방 데이터를 고치지 않는다(판례 2026-11-06-room-no-expiry). 새 모델의 바닥 접점과 크기는
  지금 충돌 상자와 맞아서 놓인 자리와 막히는 곳이 전과 같다.
- **FR-006**: 방 목록·방 만들기의 테마 미리보기 그림(`scripts/theme-previews.ts`)과 003 기준 화면은 새 모습으로 다시 만든다.

**경기장 블록·섬·배경**

- **FR-007**: 블록 모델은 격자 칸(1m 정육면체)을 정확히 채운다. 모습이 판정 크기를 바꾸지 않는다(004 FR-015, FR-019).
- **FR-008**: 블록 종류는 색과 함께 모양·질감(윤곽, 무늬)으로 구분된다. 내구가 2 이상인 블록은 남은 내구 단계마다 다른 모습(금 간 단계)을 가진다.
- **FR-009**: 블록 종류·단계의 모습은 004의 모습 목록(FR-030a, `LOOKS`) 한 곳에서 정한다. 새 종류는 모습 목록 한 줄과 아틀라스 칸 하나로 더한다.
  2D 옆 그림의 블록 색도 같은 목록에서 읽는다.
- **FR-010**: 경기장 판 아래와 둘레에 섬(땅·바위·풀)을 둔다. 섬은 판정이 없고(충돌체 없음) 넉아웃 높이·경기장 영역을 바꾸지 않으며, 떨어지는 참가자를 가리지 않는다.
- **FR-011**: 경기장의 하늘·배경·조명은 그 방 테마의 분위기를 따른다(카페는 해 질 녘, 도서관은 밤, 정원은 낮). 경기장 밖은 빈 단색이 아니다.

**조명**

- **FR-012**: 실시간 조명은 테마의 해(그림자를 드리우는 유일한 조명)와 반구광, 그리고 그림자 없는 점광 2개 이하다. HDRI·반사 환경은 쓰지 않는다
  (판례 2026-11-11-no-reflection-env). 조명 기구의 빛은 자체 발광 재질과 에셋에 구워 넣은 음영(정점 색·구운 그림자)으로 표현한다.
- **FR-013**: 해의 그림자는 참가자가 있는 곳(방 또는 경기장)을 덮는다. 경기장에서는 블록·참가자가 판과 섬에 그림자를 드리운다(003 FR-002를 경기장으로 넓힘).

**측정과 검사**

- **FR-014**: 측정 도구(`tests/bench/perf-scene`)는 앱 코드에 훅을 두지 않고 페이지의 WebGL 호출을 세어 시점마다 드로우콜·삼각형(본 패스·그림자 패스),
  텍스처 메모리, 프레임 시간, 긴 작업 시간을 낸다. 같은 방법으로 프로덕션 빌드도 잴 수 있다.
- **FR-015**: GPU와 무관한 항목(드로우콜, 삼각형, 텍스처 메모리, 에셋 전송량)은 PR마다 자동으로 예산과 비교하고, 넘으면 시점·항목·값을 알리며 실패한다.
- **FR-016**: 프레임 시간은 기준 휴대폰에서 미리보기 배포로 잰다. 이를 위해 주소에 `?perf`를 붙이면 화면 구석에 프레임 시간(p50·p95)과
  드로우콜·삼각형을 보여 준다. 이 표시는 개인정보를 남기거나 보내지 않고, 문구는 i18n 키로 둔다.
- **FR-017**: 첫 로드 검사(`tests/e2e/perf.spec.ts`)는 새 에셋 경로를 모두 세고, 맵 몫과 캐릭터 몫을 따로 예산과 비교한다.

**공통 제약**

- **FR-018**: 방 이동·채팅·신고·2D 전환과 004의 경기장 놀이는 그대로 동작하고, 기존 E2E가 통과한다.
- **FR-019**: 새로 저장하는 데이터는 없다. 화면 문구는 i18n 키로 둔다.

### 성능 예산

측정 조건과 기준선은 [research.md R1](research.md)에 있다. "혼자"는 그 시점에 나만 있는 상태, "20명"은 한 채널이 찬 상태다.
캐릭터 몫(아바타의 삼각형·드로우콜·에셋)은 005의 예산이고, 아래 "전체" 줄은 005 몫을 포함한 상한이다.

| 항목 | 상한 | 측정 방법 |
|---|---|---|
| 방 시점(혼자) 드로우콜 | 본 패스 40, 그림자 패스 40 | perf-scene, 테마별 스폰 시점 프레임 중앙값 |
| 방 시점(혼자) 삼각형 | 본 패스 60k, 그림자 패스 60k | 같음 |
| 경기장 시점(혼자, 기본 경기장) 드로우콜 | 패스마다 블록 ≤ 블록 종류 수, 섬·배경 ≤ 15, 경기장에 있을 때 방 인테리어 0 | perf-scene, 테마별 시작 칸 시점 |
| 경기장 시점 삼각형 | 블록: 기본 경기장 30k, 블록 2,000개 60k. 섬·배경 15k | 같음(2,000개는 도구가 블록을 채운 경기장) |
| 그림자 패스 | 그림자 조명 1개, 맵 크기 휴대폰 1024², PC 2048². 모든 시점에서 그림자 패스 드로우콜·삼각형 ≤ 본 패스 | perf-scene(패스별), 코드 검사 |
| 전체(20명 경기장) | 본 패스 드로우콜 100, 삼각형 150k | perf-scene, 19명 가짜 참가자 |
| 텍스처 | 맵 색 텍스처는 테마당 아틀라스 1장, 블록·섬 아틀라스 1장, 각 1024² 이하이고 512²를 넘으면 GPU 압축 형식. GPU 텍스처 메모리(그림자 맵 포함) 휴대폰 24MB | perf-scene `textureMB`, 에셋 검사 |
| 4G 첫 로드 | 001 SC-001 10초 유지. 첫 3D 에셋 3MB 중 맵(그 테마 인테리어) 1.5MB, 캐릭터 1.5MB(005). 경기장·섬 에셋 0.5MB는 첫 이동 뒤에 받는다 | perf.spec(Fast 4G, gzip 프록시, 판례 2026-11-09-perf-4g) |
| 경기장 입장 | 입구를 밟고 섬이 다 보이기까지 Fast 4G에서 3초 | perf.spec에 단계 추가 |

### Key Entities

- **모습 목록(LOOKS)**: 004 FR-030a의 한 곳. 이 기능에서 블록 종류별 모델·아틀라스 칸·내구 단계 모습, 섬·배경, 테마별 경기장 조명을 더한다.
- **테마 모습(look)**: 001·003의 테마 모습에 고정 인테리어와 경기장 배경 분위기를 더한다. 판정에 쓰이는 테마 필드(경계·스폰·입구·기본 오브젝트)는 바뀌지 않는다.
- **성능 예산**: 위 표. 측정 도구와 검사가 읽는 숫자는 한 곳에 두고 스펙 표와 맞춘다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영자가 기준 화면(테마 3개 × 방 스폰 시점, 테마 3개 × 경기장 시작 시점, 블록 종류·내구 단계 모음)을 보고 "아쉽지 않다"고 판정한다.
- **SC-002**: 성능 예산 표의 모든 항목을 지킨다. GPU와 무관한 항목은 PR마다 자동으로, 프레임 항목은 미리보기에서 기준 기기로 확인한다.
- **SC-003**: 001 SC-001(4G 10초)과 004 SC-002(때린 화면 이펙트 0.1초)를 계속 지킨다.
- **SC-004**: 이 기능 전에 만든 방이 모두 같은 자리·같은 충돌로 열린다(옛 가구 id 전부, 단위 테스트와 E2E).
- **SC-005**: 처음 보는 사람 3명이 테마 이름 없이 방 스폰 화면만 보고 테마를 맞히고, 경기장 화면에서 흙과 돌을 구분한다(운영자와 지인 시험).

## Assumptions

- 기준 저사양 휴대폰은 2021년 무렵의 보급형 안드로이드(갤럭시 A12·A13급, Mali-G52 계열 GPU)다. 기기가 없으면 운영자 휴대폰으로 재고 차이를 기록한다.
- 컨테이너·CI의 소프트웨어 WebGL은 휴대폰 프레임을 대신하지 못한다(004 T056). 드로우콜·삼각형·텍스처는 GPU와 무관해 거기서 잰 값이 실제 값이다.
- 첫 3D 에셋 상한 3MB(판례 2026-11-11-no-reflection-env)는 그대로이고 맵과 캐릭터가 반씩 쓴다. 005가 다르게 나누자고 하면 합 3MB 안에서 두 스펙을 함께 고친다.
- 에셋 제작 도구(생성 AI·DCC)는 005가 정한 것을 쓴다. 이 스펙은 결과물의 스타일·예산·출처 기록만 정한다.
