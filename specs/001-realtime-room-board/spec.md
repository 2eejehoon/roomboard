# Feature Specification: 실시간 3D 방 게시판 v1

**Feature Branch**: `speckit/kickoff`

**Created**: 2026-11-06

**Status**: Draft

**Input**: 이슈 #1 "킥오프: 확정된 결정 사항 (Spec Kit 입력)" — 게시글 하나가 실시간 3D 방 하나가 되는
게시판. 로그인·개인정보 없이 익명으로 방을 만들고, 들어가서 다른 사람과 아바타로 함께 움직이며 채팅한다.

## 용어

- **게시글(방)**: 게시판의 글 하나. 글 하나가 곧 방 하나다. 이 문서에서 "방"과 "게시글"은 같은 것을 가리킨다.
- **테마**: 방의 기본 공간과 분위기를 정하는 미리 만들어진 선택지.
- **방 데이터**: 방을 표현하는 데이터(테마 id + 오브젝트 목록).
- **채널**: 한 방의 동시 접속 그룹. 한 채널에는 최대 20명이 있고, 넘치면 같은 방의 새 채널이 생긴다.
- **익명 신원**: 기기마다 만들어지는 랜덤 키와 랜덤 닉네임. 개인정보를 담지 않는다.
- **3D 화면 / 2D 화면**: 같은 방 상태를 3D로 보여주는 화면과, 텍스트로 보여주는 대체 화면.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 방에 들어가서 다른 사람과 함께 움직이기 (Priority: P1)

방문자가 게시판 목록에서 방 하나를 고르면 그 방에 바로 들어간다. 자기 아바타를 3인칭으로 움직이고,
같은 방에 있는 다른 사람들의 아바타가 움직이는 모습을 실시간으로 본다. PC에서는 키보드로,
휴대폰에서는 화면의 가상 조이스틱으로 움직인다.

**Why this priority**: "글 = 함께 머무는 방"이 이 제품의 핵심 가치다. 이것만 있어도 미리 만들어 둔
방에서 실시간 멀티플레이를 보여줄 수 있다.

**Independent Test**: 미리 만들어 둔 방 하나에 브라우저 두 개로 들어가서, 한쪽에서 아바타를 움직이면
다른 쪽 화면(3D와 2D 모두)에 위치 변화가 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 방문자가 처음 접속했고, **When** 아무 방에 들어가면, **Then** 별도 가입 없이 랜덤 닉네임이
   붙은 아바타로 방에 나타난다.
2. **Given** 두 방문자가 같은 방 같은 채널에 있고, **When** 한 명이 아바타를 움직이면, **Then** 다른 한
   명의 화면에서 1초 안에 그 아바타가 움직인다.
3. **Given** 방문자가 휴대폰으로 접속했고, **When** 가상 조이스틱을 끌면, **Then** 아바타가 그 방향으로
   움직인다.
4. **Given** 방문자가 PC로 접속했고, **When** 이동 키를 누르면, **Then** 아바타가 그 방향으로 움직인다.
5. **Given** 방 안에 다른 사람이 있고, **When** 그 사람이 방을 나가면, **Then** 남은 사람들의 화면에서
   그 아바타와 참가자 목록 항목이 사라진다.
6. **Given** 아바타가 벽이나 가구 쪽으로 움직이고, **When** 부딪히면, **Then** 통과하지 못하고 멈춘다.

### User Story 2 - 2D 대체 화면으로 방 이용하기 (Priority: P1)

WebGL을 쓸 수 없는 기기나 브라우저, 스크린 리더 사용자, 검색 엔진은 방을 텍스트로 본다. 방 제목,
테마, 지금 있는 참가자, 채팅을 읽을 수 있고, 같은 방에 들어가 채팅하고 신고할 수 있다.

**Why this priority**: 헌법 원칙 V(2D 대체 화면 필수)다. 접근성과 SEO를 지키고, 자동 테스트가 방 상태를
확인하는 기준 화면이 된다. P1 스토리와 함께 출시해야 한다.

**Independent Test**: WebGL을 끈 브라우저로 방에 들어가서 2D 화면이 자동으로 뜨고, 다른 브라우저(3D)의
참가자 입장·퇴장·이동이 2D 화면에 반영되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 방문자의 환경에서 WebGL을 쓸 수 없고, **When** 방에 들어가면, **Then** 2D 화면이 자동으로
   보이고 오류 화면은 보이지 않는다.
2. **Given** 방문자가 3D 화면을 보고 있고, **When** 2D 전환을 누르면, **Then** 같은 방에 머문 채 2D
   화면으로 바뀐다(다시 3D로도 돌아갈 수 있다).
3. **Given** 2D 화면을 보고 있고, **When** 다른 참가자가 들어오거나 나가면, **Then** 참가자 목록이
   바로 갱신된다.
4. **Given** 검색 엔진이나 스크립트 없는 클라이언트가 방 주소를 요청하면, **Then** 방 제목과 설명을
   텍스트로 읽을 수 있다.

---

### User Story 3 - 방 만들기 (Priority: P2)

방문자는 제목과 짧은 설명을 쓰고, 테마 몇 개 중 하나를 고르고, 글 비밀번호를 정해서 새 방을 만든다.
만들면 그 방이 게시판 목록 맨 위에 나타나고, 만든 사람은 바로 그 방에 들어간다.

**Why this priority**: 사용자가 직접 글을 쓸 수 있어야 게시판이 된다. 다만 P1은 미리 만든 방만으로도
검증할 수 있어서 P2다.

**Independent Test**: 방 만들기 양식을 채워 제출하면 목록에 새 방이 생기고, 다른 브라우저에서 그 방에
들어갈 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 방문자가 방 만들기 화면에 있고, **When** 제목·테마·비밀번호를 채워 제출하면, **Then** 새
   방이 목록 맨 위에 나타나고 만든 사람은 그 방에 들어간다.
2. **Given** 제목이 비었거나 길이 제한을 넘고, **When** 제출하면, **Then** 방이 만들어지지 않고 어떤
   항목이 잘못됐는지 보여준다.
3. **Given** 봇 확인을 통과하지 못했고, **When** 제출하면, **Then** 방이 만들어지지 않는다.
4. **Given** 같은 방문자가 짧은 시간에 방을 계속 만들고, **When** 허용 횟수를 넘으면, **Then** 잠시 후
   다시 시도하라는 안내를 받는다.

---

### User Story 4 - 방 안에서 채팅하기 (Priority: P2)

방에 있는 사람들은 텍스트로 대화한다. 메시지는 같은 채널에 있는 사람에게 실시간으로 보인다. 욕설은
걸러지고, 너무 빠르게 보내면 제한된다. 문제 있는 메시지는 신고할 수 있다.

**Why this priority**: 함께 있는 경험을 대화로 완성한다. 이동만으로도 P1 가치가 있어서 P2다.

**Independent Test**: 같은 방 같은 채널의 두 브라우저에서 한쪽이 메시지를 보내면 다른 쪽에 보이고,
금칙어가 걸러지고, 연속 전송이 제한되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 두 방문자가 같은 채널에 있고, **When** 한 명이 메시지를 보내면, **Then** 다른 한 명의
   화면(3D·2D 모두)에 1초 안에 닉네임과 함께 보인다.
2. **Given** 메시지에 금칙어가 있고, **When** 보내면, **Then** 금칙어 부분이 가려져서 전달된다.
3. **Given** 방문자가 허용 속도보다 빠르게 메시지를 보내고, **When** 한도를 넘으면, **Then** 넘은
   메시지는 전달되지 않고 보낸 사람에게 잠시 기다리라는 안내가 보인다.
4. **Given** 다른 채널에 있는 사람이 있고, **When** 메시지를 보내면, **Then** 다른 채널 사람에게는
   보이지 않는다.
5. **Given** 문제 있는 메시지가 보이고, **When** 신고를 누르면, **Then** 신고가 접수됐다는 안내가 보이고, 그 메시지 내용이 신고와 함께 보관된다.

---

### User Story 5 - 인원이 많을 때 채널 자동 분리 (Priority: P2)

인기 있는 방에 20명이 넘게 몰리면, 새로 들어오는 사람은 같은 방의 다른 채널로 자동 배정된다.
방문자는 지금 몇 번 채널에 있는지 알 수 있다.

**Why this priority**: 실제 사용자를 받는 서비스에서 한 공간이 무한정 붐비지 않게 하는 안전장치다.

**Independent Test**: 한 방에 테스트 참가자 21명을 넣었을 때 21번째 참가자가 다른 채널에 배정되고,
첫 채널 참가자에게는 21번째 참가자가 보이지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 한 방의 모든 채널이 20명으로 가득 찼고, **When** 새 방문자가 들어오면, **Then** 새 채널이
   열리고 그 방문자는 새 채널에 배정된다.
2. **Given** 여유 있는 채널이 있고, **When** 새 방문자가 들어오면, **Then** 새 채널을 만들지 않고 여유
   있는 채널에 배정된다.
3. **Given** 방문자가 방 안에 있으면, **Then** 화면에서 현재 채널 번호를 볼 수 있다.

---

### User Story 6 - 내 글 수정·삭제 (Priority: P3)

방을 만든 사람은 만들 때 정한 글 비밀번호로 제목·설명·테마를 고치거나 방을 지운다. 로그인이 없으므로
비밀번호를 아는 사람이 곧 글 주인이다.

**Why this priority**: 게시판의 기본 기능이지만, 없어도 핵심 경험은 성립한다.

**Independent Test**: 맞는 비밀번호로 수정·삭제가 되고, 틀린 비밀번호로는 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 방 주인이 맞는 비밀번호를 넣고, **When** 제목을 고치면, **Then** 목록과 방 안에 바뀐 제목이
   보인다.
2. **Given** 틀린 비밀번호를 넣고, **When** 수정이나 삭제를 시도하면, **Then** 거부되고 아무것도
   바뀌지 않는다.
3. **Given** 틀린 비밀번호를 짧은 시간에 반복해서 넣으면, **When** 허용 횟수를 넘으면, **Then** 잠시
   동안 시도가 막힌다.
4. **Given** 방 안에 사람이 있고, **When** 주인이 방을 지우면, **Then** 안에 있던 사람들은 방이
   삭제됐다는 안내와 함께 목록으로 돌아간다.

---

### User Story 7 - 신고와 관리자 삭제 (Priority: P3)

방문자는 문제 있는 방이나 채팅 메시지를 신고한다. 관리자는 신고 목록을 보고 방을 지우거나, 신고된
메시지 스냅샷을 검토해 처리한다.

**Why this priority**: 실제 서비스 운영에 필요하지만, 사용자 경험의 핵심 흐름은 아니다.

**Independent Test**: 방문자가 방을 신고하면 관리자 화면 신고 목록에 나타나고, 관리자가 지우면 목록과
방 주소에서 사라지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 방문자가 방을 보고 있고, **When** 신고 사유를 골라 신고하면, **Then** 신고가 접수됐다는
   안내가 보인다.
2. **Given** 같은 기기에서 같은 대상을 다시 신고하면, **Then** 중복 신고로 처리되어 한 번만 집계된다.
3. **Given** 관리자가 신고 목록을 보고 있고, **When** 방을 삭제하면, **Then** 그 방은 목록에서 사라지고
   방 주소로 들어가면 "삭제된 방" 안내가 보인다.
4. **Given** 관리자가 아닌 사람이, **When** 관리자 기능에 접근하면, **Then** 거부된다.

---

### Edge Cases

- 방에 있는 동안 연결이 끊기면, 자동으로 다시 연결을 시도하고 그동안 "다시 연결 중" 상태를 보여준다.
  다시 연결되면 같은 닉네임으로 돌아온다.
- 같은 기기에서 같은 방을 탭 두 개로 열면, 각 탭은 별도 참가자로 보인다.
- 방이 삭제된 뒤 예전 주소로 들어오면 "삭제된 방" 안내를 보여준다.
- 존재하지 않는 방 주소로 들어오면 "없는 방" 안내와 목록으로 가는 길을 보여준다.
- 기기 저장소를 지웠거나 쓸 수 없는 환경이면, 새 익명 신원이 만들어진다(이전 닉네임은 이어지지 않는다).
- 채팅 메시지가 길이 제한을 넘으면 보내지 않고 안내한다.
- 방이 비어 있으면(참가자 0명) 목록에서 "지금 0명"으로 보인다.
- 실시간 연결 자체를 쓸 수 없는 네트워크면, 방 정보는 2D 화면으로 읽을 수 있되 이동·채팅은 쓸 수
  없다는 안내를 보여준다.

## Requirements *(mandatory)*

### Functional Requirements

**게시판과 방**

- **FR-001**: 시스템은 방 목록을 만든 시각 기준 최신순으로만 보여줘야 한다(인원순 정렬 없음). 각 항목에는 제목, 테마, 현재 접속 인원이 있다.
- **FR-002**: 방문자는 제목(필수), 설명(선택), 테마(필수, 미리 정한 목록 중 하나), 글 비밀번호(필수)로
  방을 만들 수 있어야 한다.
- **FR-003**: 방은 방 데이터(테마 id + 오브젝트 목록)로 저장되어야 한다. v1에서 오브젝트 목록은 테마
  기본값으로 채워지고, 사용자가 직접 편집하는 기능은 없다.
- **FR-004**: 방 만들기는 봇 확인을 통과해야 하고, 요청 횟수 제한을 받아야 한다.
- **FR-005**: 글 비밀번호를 아는 사람은 방의 제목·설명·테마를 수정하거나 방을 삭제할 수 있어야 한다.
- **FR-006**: 글 비밀번호는 원문을 복원할 수 없는 형태로만 저장되어야 한다.
- **FR-007**: 비밀번호 확인 실패가 반복되면 일정 시간 동안 시도를 막아야 한다.
- **FR-008**: 방은 주인이나 관리자가 지우기 전까지 남아야 한다. 비활성 기간에 따른 자동 삭제나 만료는 없다.

**실시간 방**

- **FR-010**: 방문자는 방에 들어가면 3인칭 아바타로 나타나고, 같은 채널 참가자들의 아바타와 이동을
  실시간으로 봐야 한다.
- **FR-011**: 아바타 이동은 PC 키보드와 모바일 가상 조이스틱을 모두 지원해야 한다.
- **FR-012**: 아바타는 방의 벽과 오브젝트를 통과하지 못해야 한다.
- **FR-013**: 한 채널의 인원은 최대 20명이어야 한다. 모든 채널이 가득 차면 새 채널을 열어 새 방문자를
  배정하고, 여유 있는 채널이 있으면 그 채널에 배정해야 한다.
- **FR-014**: 방 안에서 현재 채널 번호와 참가자 목록(닉네임)을 볼 수 있어야 한다.
- **FR-015**: 연결이 끊기면 자동으로 다시 연결을 시도하고, 그 상태를 사용자에게 보여줘야 한다.
- **FR-016**: 방이 삭제되면 안에 있던 참가자에게 알리고 목록으로 돌려보내야 한다.

**채팅**

- **FR-020**: 같은 채널 참가자끼리 텍스트 메시지를 실시간으로 주고받을 수 있어야 한다.
- **FR-021**: 메시지의 금칙어는 전달 전에 가려져야 한다.
- **FR-022**: 메시지 전송에는 참가자별 속도 제한이 있어야 하고, 한도를 넘으면 보낸 사람에게 알려야 한다.
- **FR-023**: 메시지에는 길이 제한이 있어야 한다.

**신원과 개인정보**

- **FR-030**: 시스템은 로그인 없이 기기마다 랜덤 키와 랜덤 닉네임으로 익명 신원을 만들어야 한다.
- **FR-031**: 시스템은 이메일, 전화번호, 실명, IP 주소 등 개인을 식별할 수 있는 정보를 저장하지 않아야
  한다. 요청 횟수 제한도 식별 정보를 저장하지 않고 해야 한다.

**신고와 관리**

- **FR-040**: 방문자는 방과 채팅 메시지를 사유와 함께 신고할 수 있어야 한다. 같은 기기의 같은 대상
  중복 신고는 기기 키 해시로 판별해 한 번만 집계한다.
- **FR-041**: 관리자는 신고 목록을 보고 방을 삭제할 수 있어야 한다. 채팅 메시지 신고는 신고 시점의
  메시지 스냅샷으로 검토하고 처리 완료(숨김)로 표시한다. 채팅 자체는 저장하지 않으므로 지울 원본이 없다.
- **FR-042**: 관리자 기능은 배포 환경 비밀값으로 둔 관리자 비밀 토큰을 제시한 요청만 쓸 수 있어야 한다.
  토큰이 없거나 틀리면 거부하고, 토큰 확인 실패에도 요청 횟수 제한을 적용한다.

**2D 대체 화면**

- **FR-050**: 모든 방 화면에는 같은 방 상태(제목, 설명, 테마, 채널, 참가자, 채팅)를 텍스트로 보여주는
  2D 화면이 있어야 한다.
- **FR-051**: WebGL을 쓸 수 없으면 2D 화면을 자동으로 보여주고, 사용자는 언제든 3D와 2D를 전환할 수
  있어야 한다.
- **FR-052**: 2D 화면에서도 방 입장, 참가자 확인, 채팅, 신고를 할 수 있어야 한다.
- **FR-053**: 방 제목과 설명은 스크립트를 실행하지 않는 클라이언트(검색 엔진 등)도 읽을 수 있어야 한다.

**다국어**

- **FR-060**: 사용자에게 보이는 모든 문구는 언어별 문구 묶음에서 가져와야 한다. v1은 한국어만 제공한다.

### Key Entities

- **방(게시글)**: 제목, 설명, 테마, 방 데이터(테마 id + 오브젝트 목록), 글 비밀번호 해시, 만든 시각,
  수정 시각, 삭제 여부. 만든 사람의 익명 키는 저장하지 않는다(소유는 비밀번호로만 증명).
- **테마**: id, 이름(문구 키), 기본 오브젝트 목록. v1에서는 미리 정한 몇 개만 있다.
- **채널**: 방에 속한 접속 그룹. 번호, 참가자 목록(최대 20명). 접속 중에만 존재한다.
- **참가자**: 채널 안의 익명 신원. 닉네임, 아바타 위치·방향. 접속 중에만 존재한다.
- **채팅 메시지**: 보낸 참가자 닉네임, 내용(필터 적용 후), 보낸 시각, 채널.
- **신고**: 대상(방 또는 메시지), 사유, 신고 시각, 처리 상태, 메시지 신고일 때 메시지 스냅샷(닉네임,
  필터 적용 후 내용, 보낸 시각), 신고 기기 키 해시(중복 판별용, 개인정보 아님). 신고자의 개인정보는
  담지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 처음 온 방문자가 목록에서 방을 골라 아바타로 움직이기까지 10초 이내에 끝난다(일반 4G
  휴대폰 기준. 일반 4G는 Chrome DevTools Fast 4G 프리셋, 판례 2026-11-09-perf-4g).
- **SC-002**: 같은 채널에서 한 사람의 이동과 채팅이 다른 사람 화면에 95% 이상 1초 안에 보인다.
- **SC-003**: 한 채널에 20명이 있어도 이동과 채팅이 SC-002 기준을 지킨다.
- **SC-004**: WebGL이 없는 환경에서 방에 들어간 방문자의 100%가 오류 화면 없이 2D 화면을 본다.
- **SC-005**: 방문자가 방 만들기를 2분 안에 끝낸다.
- **SC-006**: 저장된 데이터 어디에도 이메일, 전화번호, IP 주소가 없다(저장 데이터 감사로 확인).
- **SC-007**: 2D 화면의 핵심 행동(입장, 참가자 확인, 채팅, 신고)을 키보드와 스크린 리더만으로 끝낼 수 있다.
- **SC-008**: 신고된 대상이 관리자 삭제 후 1분 안에 목록과 방 주소에서 보이지 않는다.

## Assumptions

- 게시글 본문은 별도로 없고, 제목과 짧은 설명이 방의 텍스트 내용이다.
- v1 테마는 3개로 시작한다.
- 아바타 모양은 기기마다 랜덤으로 정해진다(고르는 기능 없음). 닉네임은 랜덤으로 정해지고 v1에서
  바꾸는 기능은 없다.
- 채팅은 접속 중인 사람에게만 실시간으로 전달하고 저장하지 않는다. 나중에 들어온 사람에게 이전 대화를
  보여주지 않는다. 예외는 신고된 메시지의 스냅샷뿐이다.
- 신고가 쌓여도 자동으로 숨기지 않고, 관리자가 검토해서 지운다.
- 방문자는 채널을 직접 고르지 않는다(자동 배정만).
- 목록은 페이지 단위로 나눠 보여준다.
- 음성 대화, 아바타 꾸미기, 방 직접 꾸미기(에디터), 다른 언어는 v1 범위 밖이다.
- 기술 스택과 무료 한도는 `/speckit-plan` 단계에서 최신 정보로 다시 확인한다.
