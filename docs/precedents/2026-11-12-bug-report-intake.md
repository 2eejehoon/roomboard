# 오류 리포트 수집: 앱 버전 형식, Worker 재가림, 수집 한도

- 날짜: 2026-11-12
- 대상: specs/002-auto-bugfix-loop research R4, data-model `github_sync_state`, contracts/github.md, FR-003·FR-011·FR-012
- 출처: PR #58(세션 판단, 운영자가 숫자를 바꿀 수 있음), PR #58 독립 리뷰
- 대체한 판례: 없음

## 결정

- 앱 버전은 `YYYYMMDDHHmm-<짧은 SHA>`(빌드 시각 UTC). 앞 12자리로 순서를 비교하고, `dev`·`unknown`은 비교 함수가 따로 다룬다.
- Worker는 클라이언트를 믿지 않는다. 문자열 필드를 다시 가리고 자르며, `frame.file`은 파일 이름만 남긴다. `appVersion`은 형식과
  현재 배포 버전 이하인지를 검사해 아니면 `unknown`으로 바꾼다. 지문은 Worker가 계산한다.
- 수집 한도: IP당 분당 10건, 전체 하루 1000건(`github_sync_state.reports_received`). 넘으면 202로 조용히 버린다.

## 이유

- FR-012 재발 판단은 "수정 버전 이후"가 필요한데 SHA만으로는 순서를 알 수 없다. 빌드 시각은 배포 워크플로가 바로 만들 수 있다.
- 리포트는 누구나 보낼 수 있고 결과는 공개 이슈에 들어간다. 가림·형식 검사를 신뢰 경계(Worker)에 두어야 개인정보와 위조 재발을 막는다.
- 분당 10건은 한 사용자 화면에서 오류가 반복돼도 충분하고, 하루 1000건은 D1 무료 한도에 비해 작다. 이슈 상한(FR-013)이 마지막 방어선이다.

## 검토한 대안

- semver(`0.3.1`): 릴리스마다 손으로 올려야 하고 지금은 릴리스 절차가 없다. 기각.
- 커밋 SHA만: 순서가 없어 재발 판단 불가. 기각.
- 하루 총량 없이 IP당 한도만: IP를 바꿔 가며 보내면 D1 쓰기가 끝없이 는다. 기각.
