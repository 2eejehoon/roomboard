# 004 plan: 한 판 상한 20명(측정), 사건 방식 서버, 같은 궤적 함수, 잠들기 대비 DO 저장소

- 대상: specs/004-knockback-brawl/spec.md SC-006(열린 질문 해소)·FR-037, plan.md, research.md R1·R2·R3·R6·R11

- 대체한 판례: 없음(FR-037 문구만 고쳤고 2026-11-18-knockback-brawl-spec의 "경기장 저장 안 함" 결정은 그대로)

## 결정

- 한 판의 인원 상한(SC-006)은 20명, 채널 정원과 같다. 경기장 입장에 따로 상한을 두지 않는다.
  - 측정: 설계를 흉내 낸 방 DO(zod 검사, 받는 사람마다 stringify·send, 궤적 계산, alarm)와 가짜 클라이언트 N명(move 초당 10, 기술 초당 3).
    모임(2m 안) N = 2~20, 흩어짐(닿지 않아 모든 move·swing이 중계되는 가장 무거운 배치) N = 12·20, 20초씩 3회.
  - 합격 기준: 기술 수신 → 마지막 상대 도착 p95 50ms, p99 100ms, 클라이언트당 50KB/s 이하.
  - N=20(R6 저장 비용 포함, PR 리뷰 뒤 다시 잼): 모임 p95 18~24ms, 흩어짐 p95 35~46ms·p99 최대 77ms·24KB/s. 기준 안이지만 p95 여유가 작다.
  - 알려진 한계: 한 DO에서 두 채널이 20명씩 싸우면(저장 비용 포함) 한 채널 p95가 51~58ms로 기준을 넘는다. 한 방 40명 넘게 모두 싸우는 경우라 MVP에서 받아들인다.
- SC-002는 때린 사람 화면의 미리 보이기로, SC-003은 서버와 모든 화면이 같은 순수 함수(1/60초 고정 간격, 반올림한 입력)로 궤적을 계산해서 지킨다.
  서버 측정은 서버가 더하는 지연에 상한을 두는 것이다.
- 서버는 tick 없이 메시지를 받을 때 판정하고, 궤적의 다음 사건(벽·착지·넉아웃)·재시작·판 제한 시간에 alarm을 건다(001 R6 그대로).
- 지은 블록과 진행 중인 판은 DO 저장소 `arena:<채널>`에 두고(블록은 2초에 한 번 씀) 채널이 비면 지운다. 잠들어도 사라지지 않게 하려는 것이고
  D1에는 쓰지 않는다. FR-037을 "영구 저장 없음, 사람이 있는 동안만 방 서버에"로 고쳤다.
- 초기값 조정 후보(값은 그대로): 방어하지 않은 강펀치는 0%에서도 넉백 세기 20.4~32.4라 돌 벽(10)을 늘 뚫고 낙법이 안 된다. 첫 시험에서
  조정표로 맞춘다(research R11). 강펀치 경직 약 5초는 경직 상한으로 해소됐다(판례 2026-11-18-hitstun-cap).

## 이유

- 20명 가장 무거운 배치에서도 기준 안이고 workerd CPU는 한 코어의 약 50%였다. 정원보다 작은 상한은 "경기장에 올라온 사람이 참가자"(FR-025)와 어긋난다.
- 사건 방식은 메시지 양이 사건 수에 비례하고, 측정한 모델과 같다.

## 검토한 대안

- 상한 12명: 근거 없이 보수적이고 입장 제한 규칙이 새로 필요하다. 기각.
- 서버 tick(60Hz): DO가 쉬지 못하고 메시지 양이 커진다. 기각. `setTimeout`: 잠든 DO에서 사라진다. 기각.
- Rapier로 넉백 궤적: 화면마다 물리 상태가 달라 SC-003을 보장할 수 없다. 기각.
- 상태를 메모리에만: 모두 가만히 있으면 DO가 잠들어 지은 경기장이 사라진다. 기각.
