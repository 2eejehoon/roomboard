# 방 만들기 양식은 서버와 같은 스키마로 먼저 검사한다

- 날짜: 2026-11-08
- 대상: specs/001-realtime-room-board/contracts/screens.md S2, quickstart.md Q7, tasks.md T061·T066
- 출처: 001 US3 화면 PR (T061, T065~T067), PR #24 리뷰 스레드(400도 rate limit에 들어감)
- 대체한 판례: 없음

## 결정

- S2는 제출 때 `createRoomRequest`(서버와 같은 zod 스키마)로 먼저 검사하고, 틀리면 요청 없이 필드 오류를 보인다.
- 400은 rate limit(3회/60초)에 들어간다. 클라이언트가 같은 스키마로 막으니 사용자가 400을 받을 일은 거의 없어 그대로 둔다.
- 403과 500처럼 siteverify를 거친 뒤의 실패에서는 위젯을 다시 받는다. 400과 429에서는 토큰을 그대로 둔다.
- Q7 E2E는 화면에서 볼 수 있는 것만 확인한다. 공백 제목은 요청을 보내지 않아야 하고, 403은 응답을 가로채 안내를 확인한다.
  서버의 400·403은 worker 테스트(T058)가 맡는다. dev 서버는 통과 테스트 키만 쓴다.

## 이유

화면에서는 400을 낼 수 없다. 예전 Q7("빈 제목 제출 → 400")은 E2E로 재현할 수 없었다.
검사 규칙을 한 곳에 두면 클라이언트와 서버가 trim이나 길이를 다르게 세는 일이 생기지 않는다.

## 검토한 대안

- rate limit을 입력 검사 뒤로 옮겨 400을 세지 않음: 잘못된 요청을 반복하는 봇에게 검사 비용을 공짜로 준다.
- E2E용 dev 서버를 실패 키로 하나 더 띄움: 403 화면 하나를 보려고 서버 두 개를 관리해야 한다.
