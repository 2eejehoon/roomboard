# 수집 한도 도달은 하루 한 번 알림, 빌드 청크 이름은 가리지 않음

- 날짜: 2026-11-13
- 대상: specs/002-auto-bugfix-loop spec Edge Cases, research R4·R5, data-model `github_sync_state.limit_alerted`, tasks T033·T036
- 출처: PR #60 리뷰(하루 한도), PR #61 리뷰(`src/worker/bug-reports.ts` 청크 이름 가림)
- 대체한 판례: 2026-11-13-bug-intake-worker(파일 이름 가림 부분만)

## 결정

- `frame.file`의 파일 이름이 `manifest.chunks`에 있으면 `redact()`를 건너뛰고, 빌드 밖 이름만 가린다. 판례 2026-11-13-bug-intake-worker의
  "실제 청크 이름은 가림 패턴에 걸리지 않는다"는 틀렸다.
- 하루 총량(1000건)에 닿은 날 Cron 동기화가 운영자에게 `[ops] 오류 리포트 하루 한도 도달 <날짜>` 이슈를 하나 연다. 본문은 날짜와 건수만,
  라벨 없음. 에이전트를 실행하지 않고 FR-013 이슈 상한에 세지 않는다.
- 한 번만 열기: 이슈를 만든 뒤 `github_sync_state.limit_alerted`를 `WHERE limit_alerted = 0` 조건으로 1로 바꾼다. 생성이 실패하면 다음 Cron이 다시 시도한다.

## 이유

- Vite 청크 이름은 `<모듈 이름>-<해시 8자>.js`다. 모듈 이름이 23자 이상이고 해시에 숫자가 있으면 긴 토큰 패턴(32자 이상)에 걸려 `[가림].js`가 되고,
  서로 다른 청크의 오류가 한 지문으로 합쳐지며 소스맵 해석(T038)도 청크를 잃는다. manifest에 있는 이름은 우리 빌드가 만든 것이라 개인정보가 없다.
- IP를 바꿔 가며 채우면 그날 수집이 멈추는데 이를 막을 값싼 방법이 없다. 운영자가 알기만 하면 한도를 올리거나 원인을 볼 수 있다.
- 플래그를 이슈 생성 뒤에 바꾸면 실패해도 알림을 잃지 않는다. 중복은 GitHub 생성 성공 뒤 D1 쓰기가 실패할 때만 난다.

## 검토한 대안

- 청크 이름을 짧게 강제(`manualChunks`·`chunkFileNames`): 빌드 설정에 규칙이 하나 더 생기고 잊으면 다시 깨진다. 기각.
- 이메일·채팅 알림: 새 비밀값과 연동이 필요하다. 이슈는 이미 있는 PAT로 연다. 기각.
- 플래그 없이 GitHub 검색으로 같은 날 알림 이슈 확인: 검색 색인이 늦어 5분 간격 Cron에서 중복이 난다. 기각.
- 공개 이슈라 공격자가 한도를 채운 것을 안다: 한도 숫자는 이미 공개 스펙에 있어 새로 드러나는 것이 없다. 받아들임.
