# 상호작용·방꾸미기는 고도화 스펙 004 하나로

- 날짜: 2026-11-12
- 대상: specs/002-auto-bugfix-loop US1·US3, 다음 기능 스펙(004), research R16
- 출처: 운영자 요청(2026-11-12, 세션 대화)
- 대체한 판례: 2026-11-12-roadmap-after-v1(순서 (3)과 범위)

## 결정

- 순서는 그대로다: 002 US1(앱 오류 자동 수집 → 이슈 → 수정 에이전트 → 리뷰 → 머지)과 US3(사용자 버그 신고) 다음에 004.
- 상호작용·방꾸미기는 큰 새 기능이 아니라 고도화 항목으로 본다(운영자). 별도 "고도화 계획" 문서는 만들지 않고,
  고도화 스펙 004 하나에 항목마다 작은 사용자 스토리로 넣어 `/speckit.specify`·`/speckit.clarify`로 시작한다.
- 후보: 혼자 하는 상호작용, 사용자끼리의 상호작용(업기, 때리기, 말걸기 등), 방꾸미기, 디자인 개선, R16 지연 로딩.
- 동작을 바꾸지 않는 리팩토링은 스펙 없이 기존 단위·E2E 테스트를 지키며 PR로 한다(헌법 III).
- 스펙에 들어가기 전에는 기능을 만들지 않는다. 운영 배포 첫 실행 확인(T108)은 끝났다.

## 이유

- 진실의 원천을 Spec Kit 하나로 둔다. 항목이 작아도 스토리 단위로 쪼개면 스펙이 무겁지 않다.
- 사용자끼리의 상호작용(때리기 등)은 상대 동의, 서버 검증, 악용 방지 규칙을 정해야 해서 clarify가 필요하다.

## 검토한 대안

- 스펙 밖에 고도화 계획 문서를 둔다: 계획과 스펙 두 곳이 어긋나고, 요구사항 결정이 기록되지 않는다. 기각.
- 항목마다 스펙을 따로 만든다(004, 005, …): 항목이 작아 스펙 수만 늘어난다. 기각.
